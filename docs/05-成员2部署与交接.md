## 1. 生成可复现部署包

在仓库根目录使用已验证的 Node.js 22.23.2，依赖尚未安装时先运行 `npm ci`，然后：

```bash
npm run prepare:deployment
```

命令没有参数，只在本地编译并生成 `artifacts/deployment/`：

| 文件 | 用途 |
| --- | --- |
| `standard-input.json` | 含所需源码与编译配置的自包含 Standard JSON Input，可用于复现编译或提交源码验证。 |
| `SeminarTickets.json`、`SeminarTickets.abi.json` | 完整编译产物及 ABI。 |
| `creation-bytecode.txt` | 创建字节码；构造函数无参数，部署金额为 0。 |
| `metadata.json`、`manifest.json` | 编译元数据、版本、设置及文件 SHA-256。 |

生成包不发送交易。`artifacts/` 是忽略的本地产物，部署成功记录需另外整理进下方证据表和报告。本次本地验证日志保存在 `artifacts/deployment/contract-tests.tap`（32 项）和 `deployment-tools-tests.tap`（8 项）。成员接入的统一 ABI 仍是 `src/config/SeminarTickets.abi.json`；合约改动后用 `npm run compile:contract` 更新它。

## 2. 部署方式与备用步骤

本次实际使用下一小节的本地辅助页与 MetaMask 部署，现有地址见本页末尾，接入时无需重复部署。以下 Remix 设置用于另一次部署时参考。

1. 在 Remix 使用 `contracts/SeminarTickets.sol`，复制当前仓库源码，保留带 `@5.6.1` 的 OpenZeppelin 导入路径。选择合约 `SeminarTickets`，不部署 `test/fixtures/` 中的测试合约。
2. 编译器选 **Solidity 0.8.30**，开启优化器，**200 runs**，EVM Version **Cancun**。这些设置与本地部署包一致。
3. MetaMask 选 **Sepolia（11155111）**；当前账户应为上方主办方地址。准备其他同学的测试钱包，主办方自己不能领票。
4. Remix 的 Deploy & Run Transactions 选择连接 MetaMask 的注入钱包环境，核对账户和网络。构造参数为空，Value 为 **0**。点击 Deploy，在 MetaMask 确认并等待成功回执。
5. 保存部署交易哈希、部署出的合约地址及 Etherscan 链接。合约地址与主办方钱包地址不同。
6. 在发生任何领票前读取：`organizer()` 等于计划地址，`seatCap() = remaining() = 50`，`totalMinted() = activeCount() = usedCount() = 0`。随后运行下一节的核验命令。

部署者永久成为主办方。本合约没有代理升级；修改合约后需重新部署并更新配置。Remix VM 和 Hardhat 的本地地址不能填作 Sepolia 地址。

### Remix 不可用时的本地辅助页

Remix 加载或文件操作异常时，可以在仓库根目录启动备用工具：

```bash
npm run preview:deployment
```

命令无参数，启动时使用相同固定编译配置生成部署产物。用安装 MetaMask 的 Chrome 打开 **http://127.0.0.1:4174**，保持终端服务运行。

1. 点击「连接 MetaMask」，在钱包里切到 Sepolia。工具只允许本次批准的 Account 2（`0x5bA8D6f1dCDb101D6a4EF905788CEBC048b2b133`）部署，Account 1（`0x03578111161a6FE000E844d3cBD2EA0F5108D7B9`）领取、退票和重新领取；其他账户或网络会阻止相应写操作。
2. Account 2 点击「部署」，核对 MetaMask 后确认。页面直接发送同一编译产物的创建字节码，构造参数为空、value 为 0，私钥留在 MetaMask 中。启动服务或连接钱包不会自动发送交易。
3. 等部署回执成功并显示合约地址后，切到 Account 1，依次领取 → 退票 → 重新领取，每步等待确认。已有合约可填地址并「加载并核对代码」，无需重复部署。页面会先核对运行时代码、固定主办方和 NFT 信息。
4. 页面收到交易哈希后立即存入当前浏览器的 `localStorage`，并显示 Etherscan 链接、回执状态和可复制的 JSON。刷新后连接同一钱包恢复查询；复制证据并保留浏览器存储。如果只有无哈希等待标记，先查 MetaMask 活动确认是否已广播，避免重复发送。
5. 保存部署和业务交易哈希后，仍按下一节运行 `verify:deployment`，生成独立的固定区块核验记录。页面的状态展示不能代替这一步。

这是成员 2 的本地开发部署工具，只提供本次部署与领票 / 退票验收入口；成员 3、4、5 的正式钱包、页面和查询工作仍待完成。部署已确认，业务验收结果仍以下方真实证据为准。

## 3. 只读核验真实部署

先查看命令说明：

```bash
npm run verify:deployment -- --help
```

本次部署的地址和哈希已填好；替换为可用的 Sepolia HTTP(S) RPC 后，可重新执行只读核验：

```bash
npm run verify:deployment -- \
  --rpc '<SEPOLIA_RPC_URL>' \
  --address '0x273d4F66420C2Bac602bdcfe4A5Bc395B1dC2dE3' \
  --organizer '0x5bA8D6f1dCDb101D6a4EF905788CEBC048b2b133' \
  --deployment-tx '0xab973e92f52498745b6add116d73b5ea1901cd94df05d649f6027e17303bd6d9' \
  --output artifacts/deployment/sepolia-verification.json
```

`--rpc`、`--address`、`--organizer` 必填；`--deployment-tx` 和 `--output` 可选。为保存完整部署证据，建议保留两项可选参数。输出文件只能位于 `artifacts/deployment/` 且扩展名为 `.json`。

脚本不使用私钥、不签名，也不修改 `.env`。它强制检查 Sepolia，在同一固定区块核对可执行运行时代码和主办方地址、容量计数、所有已铸票的所有者/状态/地址映射；提供部署哈希时还检查成功回执、创建地址和发送方。成功才会输出 `verified: true` 并写入指定文件。

运行时代码比较会填入主办方 immutable 值并排除 Solidity 元数据尾部。结果另列 `metadataMatchesPrepared` 和 `creationBytecodeMatchesPrepared`；这些值为 `false` 时要核对 Remix 源文件路径及编译设置，保留差异说明。脚本结果不是 Etherscan 的公开源码验证认证。初次部署应有 `state.isInitialState: true`；已有业务操作后可再次核验，此值为 `false` 属于正常情况。

本次[初始核验记录](evidence/sepolia-initial.json)已通过：区块 `11984383`，runtime、creation bytecode、metadata 匹配均为 `true`，主办方一致，余票 50，已铸造 / 有效 / 已核销票数均为 0。
