# 转让、退票与票务流程

进度更新：2026-11-03。以下是小组产品规则，不是老师规定的题目。`contracts/SeminarTickets.sol` 已实现合约逻辑，完整 ABI 由编译生成到 `src/config/SeminarTickets.abi.json`，并由 `src/config/contract.js` 导入。合约已部署 Sepolia 并通过初始核验，记录见 [docs/05](05-成员2部署与交接.md)。正式钱包、只读查询和三个页面均已有实现；领取 → 退票 → 同票号重领已在 Sepolia 验收。队友另已提供领取、转让、退票哈希，正式网页完整测试说明、截图及核销成功记录仍需归档。

## 产品故事

学生社团举办免费讲座，有 50 个座位。同学领取 NFT 票；不能来时可以把票转给另一位同学，或者退回主办方，让其他同学重新领取。主办方在入场时核销当前持有人的票。

这里的「退出」指退票，不是退出钱包连接。票免费，所以退票不涉及退款。每个写操作仍需要签名并支付测试网 gas。

> Students claim a free seminar ticket, transfer it to another student, or return it to the organizer so the seat can be claimed again. The organizer checks in the current ticket holder once.

## 角色

- 主办方：部署合约的钱包地址，构造时记为 `organizer`，本版固定不变。接收退票，并且只有这个地址可以核销。
- 同学：其他钱包地址。可以领票；当前持有人可以转让或退票。
- 合约地址、主办方钱包地址、持票同学地址是三个不同的地址。退票目的地是 `organizer` 钱包，不能填成合约地址。

本版演示用部署者钱包直接当工作人员钱包，不另加工作人员授权管理。

## 四个操作

| 操作 | 谁发交易 | 条件 | 成功结果 | 剩余座位 |
| --- | --- | --- | --- | --- |
| 领取 | 同学 | 有空位、当前没有有效票、这个地址未入场、不是主办方 | 拿到一张有效票 | -1 |
| 转让 | 当前持有人 | 票未核销；接收方是另一有效地址，没有有效票、未入场、不是主办方 | NFT 和入场资格一起转给接收方；原持有人失去资格 | 不变 |
| 退票 | 当前持有人 | 票未核销 | NFT 转给主办方，变为可重新领取，原持有人失去资格 | +1 |
| 入场核销 | 主办方 | 票处于有效状态，当前持有人尚未入场 | 标记这张票和该地址已入场，清空该地址的有效票号 | 不变 |

转让给自己、零地址、合约自身地址都拒绝。专用 `transferTicket(to, tokenId)` 还拒绝主办方地址，退票应使用 `returnTicket(tokenId)`。直接通过标准 ERC-721 转移入口转给主办方时，合约会按退票处理并释放名额。

## 票与地址分别记什么

票的状态按 `tokenId` 记录，不能只按最初领票地址记录。每张票有三种状态：

| 状态 | NFT 在谁手里 | 能做什么 |
| --- | --- | --- |
| `AVAILABLE = 0` 可领取 | 已铸造的退回票在主办方钱包；尚未铸造的名额还没有 NFT | 通过 `claim()` 分配给同学 |
| `ACTIVE = 1` 有效 | 当前同学 | 转让、退票，或由主办方核销 |
| `USED = 2` 已核销 | 入场同学，保留纪念票 | 查看记录；不能转让、退票或再次核销 |

尚未铸造的名额不是一张状态为 0 的 NFT。对不存在的 `tokenId` 查询或操作，要明确报错。

地址另有三个查询：

- `activeTicketOf(address)`：当前有效票号，没有则返回 0。票号从 1 开始。
- `hasEntered(address)`：这个地址是否已经入场。
- `enteredTicketOf(address)`：已核销的纪念票号，未入场则返回 0；核销时写入，刷新页面后仍可找回纪念票。`hasEntered` 根据此票号是否为 0 判断。

领取或接收转让的条件是「当前没有有效票，并且未入场」，不再使用永久的 `hasClaimed(address)` 作为资格限制。转出或退票后可重新领取或接收票。已入场地址不能再领取或接收票。

ERC-721 的 `balanceOf` 不能单独判断是否有入场资格：已经核销的纪念票仍然算在钱包 NFT 余额里。

「我的门票」先查 `activeTicketOf(account)`；为 0 时再查 `enteredTicketOf(account)`。有票号后读取 `ownerOf(tokenId)` 和 `ticketState(tokenId)`。核销后有效票号会归零，不能因此显示成无票，也不能只靠页面内存保留纪念票号。

## 退票与重新领取

1. 同学调用 `returnTicket(tokenId)`，合约验证调用者是当前持有人、票未核销。
2. NFT 所有权转到 `organizer`，状态改为可领取，清空原持有人的有效票号，并把剩余座位加一。
3. 把退回票号放进可重新发放的池中，每张退票只进入一次。
4. 下一次 `claim()` 优先发放池中的退回票，沿用相同 `tokenId`；多张退票按后退先领顺序复用，没有退回票时才铸造新票。

主办方接收退票，不需要再签一次接收交易。同学不能替主办方签名；重新发放由合约按 `claim()` 规则执行。主办方持有退回票不代表取得入场资格，也不能任意取走同学手中的有效票。

总共最多铸造 50 张票，退票后复用原票，不靠不断铸造新票释放名额。计数保持：

```text
剩余可领座位 + 有效票数量 + 已核销票数量 = 50
```

退票减少有效票数量，增加可领座位；转让只改变所有者；核销把有效票数量转成已核销票数量。已入场座位不能再次出售或发放。

## 已实现的合约接口

以下接口已由 `SeminarTickets.sol` 提供。钱包和只读查询模块已使用 `src/config/contract.js` 导出的完整 ABI 接入所需接口，不再手写旧接口列表。

| 函数 | 用途 |
| --- | --- |
| `claim() returns (uint256 tokenId)` | 领取：优先复用退票，否则铸造新票 |
| `transferTicket(address to, uint256 tokenId)` | 当前持有人转给另一同学；拒绝主办方地址 |
| `returnTicket(uint256 tokenId)` | 当前持有人退回主办方 |
| `admit(uint256 tokenId)` | 主办方核销票号及其当前持有人 |
| `organizer() view returns (address)` | 部署者 / 主办方钱包 |
| `remaining() view returns (uint256)` | 剩余可领座位 |
| `seatCap() view returns (uint256)` | 总容量 50 |
| `activeTicketOf(address account) view returns (uint256)` | 地址当前有效票号，0 代表没有 |
| `hasEntered(address account) view returns (bool)` | 地址是否入场 |
| `enteredTicketOf(address account) view returns (uint256)` | 地址已核销的纪念票号，0 代表没有 |
| `ticketState(uint256 tokenId) view returns (uint8)` | 已存在票号的状态 |
| `ownerOf(uint256 tokenId) view returns (address)` | ERC-721 当前所有者 |
| `totalMinted() view returns (uint256)` | 已铸造 NFT 总数；复用退票时不增加 |
| `activeCount() view returns (uint256)` | 当前有效票数 |
| `usedCount() view returns (uint256)` | 已核销票数 |

旧的 `admit(address)` 改为 `admit(uint256)`；旧的 `hasClaimed(address)`、`admitted(address)` 改为上表的票号和入场查询。当前交易、查询和页面均沿用这些接口。ethers v6 读取的票号和计数是 `bigint`；状态值先明确转换再与 `0`、`1`、`2` 比较。

业务事件是 `TicketClaimed(account, tokenId, reused)`、`TicketTransferred(from, to, tokenId)`、`TicketReturned(account, tokenId)`、`TicketAdmitted(account, tokenId)`。地址和票号均带索引，领取事件的 `reused` 区分新铸造和复用退票。沿用 ERC-721 的 `Transfer` 事件验证实际所有权；核销只改票状态，不转移 NFT。

### 合约统一执行的规则

- 标准 ERC-721 转移入口也必须执行相同的业务规则，包括授权后的转移；不能只在 `transferTicket()` 包装函数里检查。
- 标准 ERC-721 转给主办方统一当退票处理；专用 `transferTicket` 要求调用者改用 `returnTicket`。主办方库存转出只能通过领取流程，避免库存和座位计数不一致。
- 已核销票的所有转移入口都拒绝。普通转让不能绕过接收方的一票限制和已入场限制。
- 所有权、票状态、地址映射、座位计数、退票池必须在一次交易内同步更新；失败则整体回退。安全转移可能调用接收方合约，应确保这些规则在回调和重入情况下也保持一致。
- 不在前端模拟剩余座位或实际转移：确认回执后重新读取链上状态。

本地编译与验证命令为 `npm run compile:contract`、`npm run test:contract`；部署步骤见 [`../contracts/README.md`](../contracts/README.md)。这些命令不会产生 Sepolia 合约地址或交易哈希。本合约是首次部署用的普通合约，没有代理升级机制。

技术参考：[OpenZeppelin ERC-721 官方文档](https://docs.openzeppelin.com/contracts/5.x/api/token/erc721)。本仓库固定使用 OpenZeppelin Contracts 5.6.1。

## 验收与演示

用主办方 O 和同学 A、B、C、D：

1. A 领取票，剩余从 50 到 49。
2. A 转给 B，剩余仍为 49；B 显示持票，A 不再拥有该票。
3. O 核销 B 的票，剩余仍为 49。B 的 `activeTicketOf` 归零，`enteredTicketOf` 保留该票号，刷新后应显示纪念票。重复核销、转让已核销票、退已核销票都失败。
4. C 再领一张，剩余到 48；C 退回 O，剩余回到 49，NFT 所有者显示 O。
5. D 领取，复用 C 退回的同一个票号，剩余到 48；O 可核销 D 当前持有的票。

合约负责人另外验证：没有票时退票失败；非持有人不能擅自转移；非主办方不能核销；有有效票或已入场的接收方不能收票；满 50 个占用座位后不能领取；退票只能释放一次；通过标准 ERC-721 转移入口不能绕过这些规则。
